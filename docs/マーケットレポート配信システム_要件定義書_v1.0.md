# マーケットレポート配信システム 要件定義書

文書版: v1.3
基準コミット（配信リポジトリ）: 096281404b06c3c67d0398ec1010e72abb85c09e
対象範囲: 本文作成、Google Drive保存、構造化、GitHub反映、マーケット分析表示
基準状態: 2026年9月22日に本番反映した改善後の構成

## 1. 目的

本文が作成されていても、対象時刻の取り違え、Drive保存の証跡不足、構造化項目の欠落、訂正版の巻き戻し、一覧と分析画面の不一致が発生すると、利用者は正しいマーケット分析を確認できない。本システムは、レポートを対象枠ごとに追跡し、保存から公開確認までを同じ版で完了させることを目的とする。

## 2. 利用者と責任分界

| 役割 | 責任 |
|---|---|
| レポート作成者 | 対象時刻を固定した本文と構造化入力を作成し、必要なデータ欠損は推測で補完しない |
| Apps Script | Drive本文の検出、対象枠・本文・構造の検証、保存証跡の確認、発行ジョブの起動 |
| 発行処理 | 正本から履歴・一覧・最新・ダッシュボードを同一版で生成し、単一コミットとして公開 |
| 運用担当 | 状態・ログ・公開ページを確認し、失敗時は原因別の復旧手順を実行 |
| 利用者 | 公開された対象時刻、データ基準日、更新状態を確認して分析を利用 |

各工程の成功は、呼び出しが正常終了したことではなく、対象レポートの版が次工程で照合できることを意味する。

## 3. 対象範囲

### 3.1 対象

- 日本時間の対象枠を固定した本文作成。
- Google Driveの指定フォルダーへの本文保存と再読取。
- 本文からの構造化データ生成、必須項目・別名・対象時刻の検証。
- `reports/<reportId>.json` を正本とした公開JSON生成。
- `latest-report.json`、`reports.json`、`dashboard.json` の派生生成。
- GitHub Pagesへの公開と、公開後のJSON・画面の照合。
- 再試行、訂正版、障害状態、監視、復旧。

### 3.2 対象外

- 市場データ提供元そのものの契約・品質保証。
- AI生成モデルの選定・学習・プロンプト管理。
- 過去の欠損データを推測値で埋めること。
- 本文の内容判断を自動的に投資助言へ変換すること。

## 4. 前提と制約

- タイムゾーンは `Asia/Tokyo` で統一する。
- Google Drive、Google Apps Script、GitHub Pagesを継続利用する。
- Apps Scriptの1回の実行時間制限を超えないよう、生成・保存・公開・確認を再開可能な段階に分ける。
- 外部サービスの遅延・429・5xx・認証切れが起こり得る。
- 既存履歴には旧形式や必須項目不足が含まれるため、過去データを推測で補完せず、検証失敗を可視化する。
- 同じ対象枠へ複数の作成・公開経路を同時に有効化しない。

## 5. 機能要件

### FR-01 対象枠の固定

ジョブ作成時に `reportId=YYYY-MM-DD_HH-MM`、`reportDate`、`reportSlot`、`timezone`、`scheduledAt` を決定する。再試行、遅延、日付またぎが発生しても、起動時刻から対象枠を再計算してはならない。

### FR-02 スケジュール

- 平日: 08:00、12:00、16:00、21:00。
- 土曜日: 08:00。
- 日曜日: 定時発行なし。
- 過去互換枠の07:00・09:00は保存・検証時の互換対象として扱えるが、新規発行の期待枠にはしない。
- 本番のタイムゾーンは日本時間とする。

### FR-03 正本と版

各レポートは `reportId` ごとに正本を持ち、少なくとも `revision`、`schemaVersion`、`bodyHash`、`sourceSnapshotId`、`driveFileId`、`driveRevision` を記録する。本文の長さを新旧判定に使用してはならない。短くなった訂正版も新しい `revision` なら採用する。

### FR-04 Drive保存

本文を保存した後、返却されたファイルIDで再読取し、本文ハッシュ、対象時刻、保存先フォルダー、Driveの版を照合する。保存応答が失われた場合は、同じハッシュと対象枠の既存ファイルを確認してから再送し、重複Docを作成しない。

### FR-05 構造化と検証

本文は、要約、テーマ、変化、材料と値動きの整合性、主導市場、ニュース、金利、資金フロー、需給・ポジション、イベント、市場別見通し、メインシナリオ、代替シナリオ、崩れる条件、引き継ぎ、結論、リスク管理、本文全体を独立項目として保持する。本文に実際に使用される別名（例: 「メイン：」「代替：」「崩れる条件：」）は共通変換で扱う。

### FR-06 状態管理

最低限、次の状態を区別する。

- `WAITING_INPUT`: 締切前に本文または入力を待っている。
- `RETRYABLE_FAILED`: 通信、429、5xx、GitHub競合など再試行可能な失敗。
- `NEEDS_REVIEW`: 対象時刻不一致、構造欠落、ハッシュ不一致、権限切れなど人の判断が必要。
- `PUBLISHED`: 対象版を公開先へ反映した。
- `VERIFIED`: 公開JSONと画面が同じ対象版であることを確認した。

本文未発見を `ok:true` や公開成功として扱ってはならない。締切後の未発行は状態と原因コードを残す。

### FR-07 単一発行

発行処理は正本から、時刻別履歴、`reports.json`、`latest-report.json`、`dashboard.json` を同一版で生成し、1つの検証済みコミットとして公開する。派生ファイルを正本へ逆流させない。未来枠は一覧に保持できるが、現在のダッシュボードの最新レポートへ採用しない。

### FR-08 公開後照合

公開後に対象 `reportId`、`revision`、`bodyHash`、対象時刻、主要構造項目を配信JSONで照合し、公開ページでもタイトル、本文、表、状態表示を確認する。確認できるまで `VERIFIED` に遷移させない。

### FR-09 再試行と冪等性

再試行は原因別に行う。通信系は上限付き指数バックオフ、認証系は設定修正待ち、形式不備は本文生成・変換へ差し戻す。再試行しても `reportId` と `revision` を変えず、同じ正本を継続する。

### FR-10 監視と通知

対象枠、現在状態、最終成功、試行回数、原因コード、Drive保存済み、GitHub反映待ち、公開確認待ち、未作成件数を記録する。締切超過、再試行打ち切り、要レビュー、復旧だけを通知し、同一障害の反復通知はまとめる。

## 6. 非機能要件

### NFR-01 信頼性

保存成功・公開成功・画面確認成功を分離し、部分成功を完了扱いにしない。通常運用では1つの対象枠について採用版を1つにする。

### NFR-02 追跡可能性

本文、Driveファイル、Drive版、構造化データ、GitHubコミット、デプロイ識別子、公開確認時刻を関連付ける。訂正版は旧版を消さず、版履歴として残す。

### NFR-03 データ保全

データ欠損や取得不能を0、古い値、推測値で埋めない。前回値を表示する場合は前回値・更新待ち・基準日を明示する。

### NFR-04 セキュリティ

認証情報・GitHubトークンを本文、ログ、ドキュメントへ出力しない。権限切れは再試行で隠さず、要レビューとして扱う。

### NFR-05 保守性

対象時刻、状態、スキーマ、別名、正本の決定を複数ファイルへ重複定義しない。設定・検証・発行の契約を変更した場合は、仕様書とマニュアルを同じ版で改訂する。

## 7. 受入基準

1. 平日4枠と土曜枠で、Drive本文、正本JSON、派生JSON、公開画面の `reportId` と `revision` が一致する。
2. 同じジョブを多重起動しても、採用Doc・公開レコードが重複しない。
3. Drive保存後に通信が切れても、再試行で既存ファイルを検出し、本文を作り直さず公開工程から再開できる。
4. 本文未到着は締切前は待機、締切後は未発行として検知される。
5. 対象時刻・本文・ファイル名の不一致は隔離され、別枠へ公開されない。
6. 将来枠は保存されても現在の最新表示を先取りしない。
7. 短くなる訂正、過去枠の訂正、古いlatestからの再同期で新しい版が巻き戻らない。
8. 保存レシート欠損、本文ハッシュ不一致、公開画面の旧版は `VERIFIED` にならない。
9. 旧履歴の不足項目は推測で補われず、検証結果と対象範囲が報告される。

## 8. 導入後の運用目標

目標値は、Drive保存確認から公開照合まで15分以内、締切超過を5分以内に検知することとする。これは実測達成値ではなく、10稼働日の観察で確認する導入目標である。評価指標は、予定枠の欠落、重複採用、訂正巻き戻し、完了報告と公開版の不一致の件数とする。

## 9. 未確定事項

- 生成側の実運用タスクと、本文作成からジョブ台帳へ渡すアダプターの正式担当。
- 通知先、当番、締切時のエスカレーション先。
- 日本の休場日でも海外市場レポートを作るかどうか。
- 初回ライブレポートの観察結果を踏まえた15分・5分目標の調整。

## 10. TradingView MCP連携要件

TradingView MCPは、TradingViewの認証済みデータ・分析機能を本文作成へ取り込む読み取り専用の入力アダプターとして扱う。本番の正本・発行処理をTradingView MCPへ移さず、既存のDrive保存、正本化、単一publisher、公開後照合を維持する。

### FR-11 入力アダプター

- 対象データは、OHLCV、テクニカル指標、経済指標、ニュース、カレンダー、スクリーナー結果とする。
- 銘柄は `EXCHANGE:TICKER` 形式で解決し、推測したティッカーを使わない。
- 取得結果に `source`、`symbol`、`interval`、`barTimestamp`、`fetchedAt`、`sourceSnapshotId`、使用ツール名を付与する。
- TradingView MCPから取得した値は、本文作成前に対象枠・基準日・単位・既存データ源との整合性を検証する。
- MCPの認証切れ、レート制限、未解決銘柄、権限制限、取得欠損は理由付きで記録し、0や推測値で補完しない。

### FR-12 本番切り替えゲート

1. Codexから読み取り専用でUSD/JPYと金を取得する。
2. 既存の検証済みデータ源と10稼働日比較する。
3. 時刻、単位、価格差、欠損、再認証、レート制限を記録する。
4. 定時の無人処理でOAuthを維持できることを検証する。
5. 差異と障害が許容範囲内であることを確認してから、対象項目ごとに本番入力元へ昇格する。

試験中はTradingView MCPを分析本文の補助入力として扱い、公開正本や本番の最新値を自動で置き換えない。

### NFR-06 入力の可観測性

TradingView MCPを利用した本文には、取得元、取得時刻、データ基準時刻、ツール名、未取得理由を追跡できること。取得経路の変更が本文・正本・公開画面で追跡不能になってはならない。

## 11. 取得元切替とロールバック要件

TradingViewを導入する場合も、取得元は設定で切り替えられること。既定値は既存の検証済みデータ源（`legacy_verified`）とし、TradingViewの導入だけで本番公開元を変更しない。

- `legacy_only`: 既存データ源だけを取得・公開する。
- `shadow`: TradingViewを比較取得するが、公開は既存データ源で行う。
- `tradingview_primary`: 昇格条件を満たした場合だけTradingViewを公開元にする。失敗時は既存データ源へフォールバックする。
- `rollback`: `legacy_only` と同じ扱いに戻し、切替理由と時刻を監査記録へ残す。

認証切れ、レート制限、タイムアウト、銘柄不一致、データ差異、古いデータ、スキーマ不正を検知した場合は、自動または運用操作で `legacy_only` へ戻せること。ロールバックは本文の再生成を必要とせず、次回取得から既存データ源を使う。取得元、基準時刻、設定版、ロールバック理由をレポートの保存証跡へ残す。

## 12. 2026-09-25の同期障害から追加した要件

08:00枠では定時の事前検証時点で本文が不完全であり、12:00・16:00枠では予定時刻に対応するGoogle Docsが見つからなかった。原本が後からDriveへ保存されてもポータル同期が自動で再開しなかったことが直接原因である。さらに21:00枠では、完全なGoogle Docs本文と同時間帯の図解がDriveに存在したが、Apps Scriptの公開前解析が本文を正しく構造化できず、公開前検証でGitHub書込みが中止された。見出しの前方一致が「メインシナリオは、」を空の見出しとして扱い、ASCII数字の広い判定が小数値の行を番号付き見出しとして扱い、市場価格が文章中に明記されていても市場データとして抽出されないことが原因だった。調査した時刻・対象キーは日本時間で整合しており、UTC変換は原因ではなかった。

### FR-13 保存遅延後の再同期

- Drive保存とポータル同期を独立工程として追跡し、Drive保存だけで公開完了にしない。
- 定時後に本文がそろった場合、同じreportIdのまま再検証・同期を再開できる。5分間隔のApps Script watchdogとGitHub Actionsの再照合を使用する。
- 再試行時も対象枠を再計算せず、本文・図解ともYYYY-MM-DD_HH-MMで照合する。
- 本文が不在・不完全、図解が不在・別時間帯、保存記録が不十分な場合は発行を止め、状態・原因・最後に成功した工程を記録する。
- 公開前解析は見出しを正規化後の完全一致または明示した別名で判定し、小数値を見出しと誤認しない。市場価格を本文から補う場合は、同一市場の本文ブロック内にある明示値だけを使う。
- 21:00を含む実レポート形式の回帰テストを継続的インテグレーションで実行し、本文解析と必須項目検証に失敗した場合は公開を止める。
- 公開完了はGitHub反映やdeployだけでは成立しない。公開URLから対象タイトル、本文、対応図解を確認して初めて完了とする。
- 実在する原本がない枠は対象データなしとする。空本文、仮数値、別日・別時刻の本文や図解を作成・流用しない。

### NFR-07 工程の可観測性

本文生成、Drive保存・再読取、Drive保存記録、正本・一覧更新、GitHub commit、deploy、公開ページ確認を別々の工程として記録する。それぞれに対象枠、成功・失敗、時刻、コミットまたは実行識別子を残す。

### 追加受入基準

10. 遅れて保存された原本は同一対象枠で一度だけ公開され、別枠へ流れない。
11. 本文と図解の時間帯キーが一致しないときは、公開とVERIFIEDへの遷移が拒否される。
12. Drive保存記録のない対象枠はポータル同期前に検出される。
13. 公開後に本文・図解・タイトルの一致を確認できないときは成功扱いにならない。
14. 原本のない21:00枠は未発行のまま表示し、空データを登録しない。
15. 既知の見出し別名を使う実レポート本文が正しく解析され、小数値・シナリオ文が見出しとして切り捨てられないことを回帰テストで確認する。
