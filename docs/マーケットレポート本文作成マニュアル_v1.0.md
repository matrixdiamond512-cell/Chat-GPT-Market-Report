# マーケットレポート本文作成マニュアル

文書版: v1.3
対象: マーケットレポート本文を作成・確認する担当者
関連文書: マーケットレポート配信システム 要件定義書 v1.3、仕様書 v1.3、運用マニュアル v1.3

## 1. 目的

本書は、マーケットレポート本文を対象時刻に合わせて作成し、構造化取込と公開検証に通る状態でGoogle Driveへ保存するための手順を定める。本文の読みやすさだけでなく、対象時刻、データ基準日、必須セクション、シナリオ、6市場の見通し、欠損表示を一貫させる。

本文作成の完了は、文章を書き終えた時点ではない。対象枠、データの時点、本文構造、数値の根拠、保存後の再読取が確認できた時点を完了とする。

## 2. 対象枠と作成前の固定事項

タイムゾーンは `Asia/Tokyo` とする。

| 曜日 | 対象時刻 |
|---|---|
| 月〜金 | 08:00、12:00、16:00、21:00 |
| 土 | 08:00 |
| 日 | 定時発行なし |

本文を作り始める前に、次の値を固定する。

- `reportId=YYYY-MM-DD_HH-MM`
- 対象日と対象時刻
- 作成日時
- 市場データ基準日・取得日時
- 対象時刻に対応する本文テンプレート

遅れて作成しても、作成時刻を対象時刻へ変更しない。未来の枠を先に作った場合は下書きとして保存できるが、現在の最新レポートとして扱わない。

## 3. 本文の標準構成

次の順序で作成する。空欄を無理に埋めず、確認できない項目は理由付きで取得不能または判定保留とする。

1. タイトル、対象時刻、作成日時、データ基準日
2. 要約
3. 今日の相場テーマ
4. 前回からの変化
5. 材料と値動きの整合性
6. 今日の主導市場
7. 重要ニュース
8. 金利
9. クロスアセット資金フロー
10. 需給・ポジション
11. 今後の重要イベント
12. 6市場の見通し
13. メインシナリオ
14. 代替シナリオ
15. シナリオが崩れる条件
16. 次の時間帯への引き継ぎ
17. 結論
18. リスク管理

6市場は、金、WTI原油、日経225先物（大阪取引所）、USD/JPY、EUR/USD、BTCUSDを独立して記載する。

公開前解析では、既知の見出しを完全一致または登録済み別名として扱う。「メインシナリオは、」のような本文の導入文や価格・小数値を見出し行として書かない。市場値を文章で記載する場合も、値は必ず該当市場の同じ節に単位とともに記し、別市場・別時間帯の値を混在させない。CIでは実本文形式の例を使って解析結果を確認する。

## 4. 時刻別の書き分け

### 08:00

昨夜のNY時間から東京時間へ引き継ぐ要因を中心に書く。米国金利、ドル、株式、コモディティ、先物の反応を材料から価格まで順に整理し、東京時間で最初に確認する条件を示す。

### 12:00

東京前場の実際の値動きを中心に書く。材料、最初に反応した市場、他市場への波及、価格反応、流れが継続したか反転したかを区別する。未確認のニュースや時刻を補わない。

### 16:00

東京時間全体を振り返り、後場の変化と欧州時間への引き継ぎを整理する。日経225先物、USD/JPY、金利、海外市場との関係を本文と表で一致させる。

### 21:00

欧州時間の流れとNY時間開始前の材料を中心に書く。16:00からの変化を独立して整理し、翌東京時間へ持ち越す条件を明示する。21:00本文を16:00本文の単純な改名で作らない。

### 土曜08:00

週末時点の週間整理として、前週からの変化、主要市場の方向、来週の重要イベント、上振れ・下振れ条件を記載する。平日枠の本文をそのまま流用しない。

## 5. データと因果関係の書き方

### 5.1 基準日と取得日時

- 基準日は、その数値が表す時点。
- 取得日時は、システムが取得・更新した時点。
- 両者が異なる場合は両方を記載する。
- 不明な日時を推測しない。

### 5.2 材料から価格まで

各主張は、できる範囲で次の順に書く。

1. 確認できた材料
2. 最初に反応した市場
3. 金利・為替・資金フロー・需給への波及
4. 価格反応
5. その後の継続、反転、または確認不能

材料と値動きの因果関係を断定できない場合は、「同時に観測された」「整合的」「判定保留」など、確認できる範囲の表現に留める。

### 5.3 欠損と前回値

- 取得不能を0、空欄、推測値で補完しない。
- 前回の確認値を表示する場合は「前回確認値」「更新待ち」と基準日を明示する。
- 前回値を今回の価格や今回の変化率として書かない。
- 重要な主値や根拠が欠ける場合は、整合性判定を保留する。

### 5.4 ゴールド需給

短期の価格発見と中期の持続需給を分けて書く。CFTC Managed Money、実質金利、ドルを価格発見側、世界金ETF、中央銀行、中国・インド現物需要を持続需給側として扱う。世界金ETFとGLD・IAUを二重に加点せず、ETFの流入・流出を当日の価格変動の直接原因と断定しない。

## 6. シナリオの書き方

本文では次の表記を推奨する。

- `メイン：` 現時点で最も妥当と考える展開と根拠
- `代替：` 反対方向または別経路の展開と成立条件
- `崩れる条件：` シナリオを撤回・見直しする観測条件

シナリオは予測値だけでなく、確認する市場、時間軸、条件を含める。条件が確認できない場合は、確度を上げる表現を避ける。

## 7. 生成前の6ゲート

### GATE 1 最新ルールの確認

本文作成前に、本書とシステム仕様書の対象枠・必須項目・欠損ルールを確認する。記憶や前回本文だけで代用しない。

### GATE 2 対象本文の固定

対象日、対象時刻、作成日時、データ基準日を作業メモへ固定する。別日・別時刻の本文を混ぜない。

### GATE 3 必須項目表

標準構成の各項目について、今回の本文内の対応箇所を確認する。項目が空の場合は、空のまま公開せず、取得不能または判定保留の理由を書く。

### GATE 4 本文確定稿

長い資料や取得結果をそのまま貼り付けず、材料→波及→価格反応→次の監視点の順に本文へ整理する。数値、日時、見出しを確定してから保存する。

### GATE 5 保存前検査

- 対象時刻とタイトルが一致している。
- 作成日時とデータ基準日が区別されている。
- 6市場が独立している。
- 必須セクション、シナリオ、引き継ぎ、結論がある。
- 数値と本文の方向感が一致している。
- 取得不能が推測値で埋められていない。

### GATE 6 保存後検査

Google Driveへ保存した後、保存したファイルIDで本文を再読取する。本文、対象枠、保存先、本文ハッシュが一致しない場合は公開へ進めず、運用マニュアルの状態別対応へ移す。

## 8. Google Drive保存ルール

1. 指定フォルダー `WEBマーケットレポート` へ保存する。
2. ファイル名に対象日・対象時刻・本文の版を含める。
3. 同名ファイルがあっても、更新日時だけで正本を決めない。
4. 訂正版は本文が短くなっても、版が新しく検証に通れば採用できる。
5. 保存成功の表示だけで完了とせず、本文の再読取を行う。

## 9. 作成者チェックリスト

### 保存後のポータル引き渡し

1. Driveファイル名、本文タイトル、reportIdが同じ対象枠であることを確認する。タイトル形式はマーケットレポート｜YYYY/MM/DD（曜日）HH:MMとする。
2. 図解を使う場合は、既存の同一YYYY-MM-DD_HH-MMの画像を選ぶ。別スロット画像の転用や再生成はしない。
3. Drive保存後にファイルIDで本文を再読取し、完全な本文と対象枠を確認する。
4. Drive保存記録、ポータル同期、GitHub Actions、deployを確認し、最後に公開URLから本文と図解を確認する。
5. 公開ページの確認前に配信完了と報告しない。原本がない枠は対象データなしとして扱う。

- [ ] 対象枠と `reportId` を固定した
- [ ] 対象時刻に合った本文テンプレートを使用した
- [ ] タイトル、対象時刻、作成日時、基準日を確認した
- [ ] 必須セクションを標準順序で確認した
- [ ] 6市場を個別に確認した
- [ ] 材料→波及→価格反応→監視点の順で整理した
- [ ] シナリオと崩れる条件を分けた
- [ ] 取得不能を推測値で補っていない
- [ ] Drive保存後の再読取とハッシュ照合を行った
- [ ] 版、対象枠、例外を保存記録へ残した

## 10. 禁止事項

- 別時刻・別日の本文を改名して流用すること。
- 作成日時を対象時刻として書き換えること。
- 前回値を当日値として表示すること。
- 取得不能を0、推測値、根拠のない方向感で埋めること。
- ETF、先物、金利など更新頻度の違うデータを同一時点の因果として断定すること。
- 6市場やシナリオを、見やすさだけを理由に省略すること。
- Drive再読取前に公開完了と報告すること。
- Drive保存が成功しただけでポータル反映済みと報告すること。
- 空のレポート、仮の市場数値、別日・別時間帯の本文や図解で未発行枠を補うこと。
- 本文が完全でない、または同時間帯の既存図解がない状態で公開すること。

## 12. TradingView MCPデータの利用

TradingView MCPから取得した値を本文へ使う場合は、TradingViewを取得元として明示し、対象銘柄、時間足、バーの基準時刻、取得時刻を確認する。銘柄は `EXCHANGE:TICKER` 形式で解決し、似た銘柄や別取引所の値を推測して使わない。

- OHLCVは、同じ対象日・時間足・単位で既存データ源と照合する。
- テクニカル指標は、時間足と計算条件を明記する。
- 経済指標・ニュースは、公開時刻、提供元、対象地域を確認する。
- MCPの取得不能、権限制限、レート制限、認証切れは本文に理由付きで示す。
- 試験期間中は、TradingViewの値だけで公開正本を置き換えない。
- 取得結果を当日の市場データとして書く場合は、バー時刻と取得時刻を混同しない。

本文作成者は、TradingView MCPの取得結果を根拠として採用する前に、本文の対象枠と市場データ基準日が一致していることを確認する。差異が解消できない場合は、前回値や推測値へ置き換えず「判定保留」または「取得不能」とする。

## 13. 変更時の扱い

本文の必須項目、時刻別構成、別名、欠損ルール、TradingView MCPの利用方針を変更する場合は、本文作成マニュアル、配信システム仕様書、運用マニュアルを同じ版で改訂する。本文だけを変更して取込仕様を変更しない状態を作らない。

## 14. 取得元切替時の本文扱い

取得元を切り替える場合も、本文の対象枠、データ基準日、取得時刻、取得元を明示する。TradingViewで差異や取得不能が発生した場合は、推測値や前回値で埋めず、既存データ源へ戻すか判定保留とする。ロールバック後に本文を再生成する場合は新しい版として保存し、既存の公開本文を後から書き換えない。

## 15. 原文の保全と構造化の例外

既存の08:00・12:00・16:00レポートが完全な原文として保存されていても、市場別の構造化数値が原文にない場合がある。アーカイブ取込では規定の文字数と対象枠の検証を通したfullTextを原文形式のまま保持し、数値やmarkets構造を推測で追加しない。この互換扱いは既存原文の移行に限り、新規本文で必須項目を省略するものではない。21:00は厳格な構造化契約を維持する。

原本または対応する図解が確認できない対象枠は発行しない。公開側で「対象データなし」と表示し、空文書や仮画像を作らない。
