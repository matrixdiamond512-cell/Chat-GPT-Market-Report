# P1 isolated Cloud Run / Scheduler / Storage trial plan

Status: preparation only. Do not enable APIs or create cloud resources until the user separately approves the exact resource list and cost below. Use the existing project selected by the owner; do not create a project. Keep this service, bucket, evidence and identities separate from production.

## Authentication and schedule contract

- Cloud Run must require IAM authentication; do not grant `allUsers`. Set one explicit audience to the canonical service URL.
- Create 12 dedicated Scheduler caller service accounts, one for each weekday publication slot (08:00, 12:00, 16:00, 21:00 JST) and attempt (T-13, T-7, T-3). Each account gets only `roles/run.invoker` on the isolated service. Configure no user-managed keys and grant no unrelated principal `iam.serviceAccounts.actAs` or Token Creator.
- Set each job's `X-CloudScheduler-JobName` expected full resource name, unique caller identity, and exact `X-CloudScheduler-ScheduleTime` mapping in the service allowlist. The HTTP body is the exact fixed bytes `{"schemaVersion":1,"trigger":"P1_SHADOW"}` for every run; it contains no reportId or market data. After verifying Google OIDC signature, issuer, expiry, audience and caller email, the service checks the exact job allowlist, UTC schedule timestamp, offset, slot and weekday. It derives the reportId from that validated scheduled time plus the configured T−13/T−7/T−3 offset, converts to the target JST slot, and passes that identity to the shadow provider. The job/time headers are not signed by the JWT, so use distinct caller service accounts, exact allowlists and restricted impersonation. Cloud Run IAM is a second gate.
- Tokyo Cloud Scheduler region `asia-northeast1`, timezone `Asia/Tokyo`. For weekdays: 07:47/07:53/07:57 → 08:00; 11:47/11:53/11:57 → 12:00; 15:47/15:53/15:57 → 16:00; 20:47/20:53/20:57 → 21:00. For each slot, those are offsets 13/7/3 minutes. No Saturday or Sunday jobs in this isolated trial.

## Minimal runtime limits

- Cloud Run service `p1-report-shadow-ingress`, region `asia-northeast1`, IAM required, 1 vCPU, 512 MiB, min instances 0, max instances 2, concurrency 1, request timeout 120 seconds, request max 1 MiB. Use a small pinned Python image; no outbound market/API acquisition or production writer.
- Runtime service account: define a custom role with only `storage.objects.create` and `storage.objects.get`, bind it only on the trial bucket with a condition restricted to `resource.name.startsWith("projects/_/buckets/<BUCKET>/objects/shadow/")`, and enable uniform bucket-level access. The adapter needs create + metadata/readback but never list, overwrite, update or delete. If custom-role setup is not practical, bucket-scoped `roles/storage.objectCreator` + `roles/storage.objectViewer` are the predefined fallback; objectViewer also grants object listing. No bucket admin, project Editor/Owner or key.
- Scheduler job creator: grant Service Account User (`roles/iam.serviceAccountUser`, `iam.serviceAccounts.actAs`) only on the 12 Scheduler caller accounts. Bind each caller account to `roles/run.invoker` only on this Run service. Verify the Google-managed Cloud Scheduler service agent has its required `roles/cloudscheduler.serviceAgent` role; do not grant that role to user accounts. Keep keys disabled and no extra Token Creator/impersonation principals.
- Deploy operator permissions remain separate: narrowly scoped Cloud Run deploy permissions, `iam.serviceAccounts.actAs` only on the runtime account, and Artifact Registry Writer only on the dedicated image repository. Do not reuse the runtime identity.
- Daily 3-minute invocation window per weekday slot means 12 invocations/business day, 276 in a 23-day month. Scheduler retries capped to 1 retry with short backoff, deadlines before the report target, plus max 2 Run instances; idempotency uses create-only objects and generation-pinned readback. Run the WSGI entrypoint as `gunicorn --bind :$PORT --workers 1 --threads 1 --timeout 120 scripts.run_report_continuity_service:app`.
- Log only reportId, slot, stage, response class and object generation/hash. Exclude tokens, full payloads, account emails and credentials. Keep logs 30 days; default project log ingestion allowance is shared across services.

## Isolated Storage and real SDK verification procedure

- Private regional bucket `p1-report-shadow-<unique-suffix>`, location `asia-northeast1`, Standard, uniform bucket-level access, public access prevention enforced, soft delete 7 days. No website hosting, replication, retention lock, or lifecycle prefix overlap with production.
- Store each scheduled attempt at its own create-only path: `shadow/<reportId>/attempts/t-13/evidence`, `.../t-7/evidence`, or `.../t-3/evidence`, plus a per-attempt immutable readback-stage object. Same attempt + same bytes is a duplicate delivery and returns `NO_OP` after readback. A later scheduled attempt is a normal new acquisition: it gets a different key and returns `CREATED`, even when its bytes differ from earlier attempts. Same attempt key + different bytes is an abnormal `CONFLICT`; do not overwrite or create a replacement for that attempt. Keep all evidence and stage objects for 30 days using a lifecycle delete rule scoped to `shadow/`; do not add a mutable latest pointer. Do not set a locked retention policy. Soft-delete permits recovery through day 7 after lifecycle deletion; review cost effect. Preserve conflicts/late evidence for manual reconciliation before cleanup.
- With a separately approved bucket and an authorized ADC identity, run the SDK path via `google.cloud.storage.Client().bucket(BUCKET)` and `GcsShadowStorage(..., enabled=True)`. Use a unique disposable reportId and an attempt-specific evidence key. Confirm upload uses `if_generation_match=0`; read back the same generation and compare exact bytes, SHA-256, positive generation and server `time_created`; repeat the same attempt key+bytes and confirm `NO_OP`. Create the other two attempt keys with distinct fixtures and confirm both are `CREATED`, then retry one attempt key with different bytes and confirm `CONFLICT` while the original bytes/generation remain unchanged. Confirm a non-shadow key is rejected before any SDK request.
- Record run ID, project/region, image digest, SDK pins, key suffix, hashes, generations, UTC server times and result. Delete only the uniquely named fixture after recording, using a separately scoped cleanup identity; never delete a conflict or production object. Do not claim a real SDK/storage pass until this procedure is run against GCS and independently read back.
