# マーケットレポート配信システム 運用マニュアル

文書版: v1.3
対象: レポート作成者、運用担当、保守担当
基準コミット（配信リポジトリ）: 096281404b06c3c67d0398ec1010e72abb85c09e

## 1. このマニュアルで確認すること

このシステムでは「本文がある」「Google Driveへ保存できた」「GitHubへ反映できた」「公開画面が新しい」という状態を分けて扱う。完了報告は、対象枠・本文・版が公開先で一致し、公開画面まで確認できた場合だけ `VERIFIED` とする。

## 2. 通常運用

### 2.1 作成前

1. 対象枠を確認する。平日は08:00、12:00、16:00、21:00、土曜は08:00、日曜は定時発行なし。
2. ジョブの `reportId` と対象日を固定する。遅れて実行しても起動時刻へ付け替えない。
3. 市場データの基準日・取得日時・取得不能理由を分けて確認する。
4. 前回レポートの本文や数値をコピーして、今回の値として残さない。

### 2.2 本文作成

本文には次の項目を独立して含める。

- 要約、今日の相場テーマ、前回からの変化。
- 材料と値動きの整合性、今日の主導市場、重要ニュース、金利。
- クロスアセット資金フロー、需給・ポジション、重要イベント。
- 金、WTI原油、日経225先物（大阪取引所）、USD/JPY、EUR/USD、BTCUSDの見通し。
- メインシナリオ、代替シナリオ、シナリオが崩れる条件。
- 次の時間帯への引き継ぎ、結論、リスク管理。

本文の見出しは完全一致でなくてもよいが、意味が同じ別名は共通変換に登録された表記を使用する。例として、「シナリオ分析」の中の「メイン：」「代替：」「崩れる条件：」は自動取込の対象である。

### 2.3 Google Driveへの保存

1. `WEBマーケットレポート` フォルダーへ保存する。
2. ファイル名に対象日と対象時刻を入れる。
3. 同名ファイルがある場合は、更新時刻だけで正本を決めず、本文・対象枠・DriveファイルIDを比較する。
4. 保存後、本文全体を再読取して対象枠とハッシュを確認する。
5. 保存が成功したように見えても、再読取できるまで公開工程へ進めない。

### 2.4 発行と確認

1. Apps Scriptの対象枠トリガーまたは再試行トリガーを確認する。
2. 実行ログで `reportId`、`revision`、状態、エラーコードを見る。
3. 正本履歴、`reports.json`、`latest-report.json`、`dashboard.json` が同じ対象版か確認する。
4. 公開ページでタイトル、対象時刻、主要市場表、シナリオ、本文、更新状態を確認する。
5. すべて一致したら `VERIFIED` と記録する。

## 3. 状態別の対応

### 3.1 `WAITING_INPUT`

締切前で本文がまだ届いていない状態。本文が見つからないことを成功として報告しない。

- 締切前: 入力待ちのまま、次の再試行時刻を確認する。
- 締切後: `INPUT_NOT_FOUND` と対象枠を記録し、未発行として通知する。
- 別時刻の本文を現在枠へ改名して埋めない。

### 3.2 `RETRYABLE_FAILED`

通信切断、429、5xx、GitHub競合など。一度、DriveまたはGitHub側に書き込みが残っていないか確認してから再試行する。

1. `reportId` と `revision` を変えない。
2. 保存済み本文がある場合は本文作成からやり直さず、保存確認または発行から再開する。
3. 再試行上限を超えたら `NEEDS_REVIEW` へ移し、原因を残す。

### 3.3 `NEEDS_REVIEW`

人の判断が必要な状態。次の事象を自動で通してはならない。

- 本文、ファイル名、ジョブの対象時刻が一致しない。
- 必須構造、6市場、シナリオ、結論が不足している。
- Drive再読取の本文ハッシュが異なる。
- 認証・権限が切れている。
- 同じ対象枠に複数の採用候補がある。
- 公開先が正本と異なる版を返す。

候補文書を本文まで比較し、採用版を決められない場合は公開せず、対象枠と候補IDをエスカレーションする。

### 3.4 `PUBLISHED` と `VERIFIED`

`PUBLISHED` はGitHubへの反映までであり、画面確認は未完了。公開JSONの取得失敗、CDNの旧版、本文と表の不一致がある間は `VERIFIED` にしない。公開確認が終わった時刻とコミットを記録する。

## 4. よくある障害と復旧

### 本文がない

対象枠を再計算せず、本文生成タスクとDriveフォルダーを照合する。締切前は待機、締切後は未発行として記録する。現在表示中のデータから過去本文を作らない。

### 同名Docが複数ある

各Docの本文、対象時刻、作成・更新時刻、DriveファイルIDを比較する。本文が同じならハッシュで採用版を1つに決め、本文が異なるなら `NEEDS_REVIEW` とする。更新時刻だけで決めない。

### 保存後に応答が切れた

同じ対象枠・本文ハッシュ・保存先で既存ファイルを検索する。見つかった場合は新しいDocを作らず、再読取して保存証跡を完成させる。

### 未来の枠が一覧に出る

未来枠を削除せず、現在のダッシュボードの最新表示から除外する。対象時刻が到来し、本文・構造・版が検証できてから最新表示へ採用する。

### 訂正版が短くなった

本文の長さを比較しない。`revision` または `updatedAt` が新しく、本文・対象枠・構造の検証が通るなら短い訂正版も採用する。旧版へ戻さない。

### 公開JSONの一部だけ新しい

`latest-report.json`、対象時刻の履歴、`reports.json`、`dashboard.json` を同じ正本から再生成する。手動で1ファイルだけ書き換えない。再生成後に4点と公開画面を照合する。

### 公開ページが旧版のまま

公開JSONのコミット、デプロイ結果、ページの読み込み結果を順に確認する。CDN・ブラウザーキャッシュが疑われても、確認前に `VERIFIED` と報告しない。

## 5. Apps Scriptの確認手順

1. Apps Scriptプロジェクトを開く。
2. `MarketReportAutoPublish.gs`、`MarketReportWebSync.gs`、`MarketReportStructuredImport.gs`、`MarketReportPrePublishValidation.gs`、`DashboardJsonSync.gs` の保存状態を確認する。
3. `ParserPatch.gs` は旧重複パーサーを無効化した互換ファイルであり、ここへ新しい解析処理を追加しない。
4. 関数 `installMarketReportAutoPublishTriggers()` を実行する。
5. トリガー一覧で本発行4件、再試行4件、5分間隔のwatchdog 1件が各1件、合計9件あることを確認する。
   - `autoPublishMarketReport0800`
   - `autoPublishMarketReport1200`
   - `autoPublishMarketReport1600`
   - `autoPublishMarketReport2100`
   - `autoPublishMarketReport0930Retry`
   - `autoPublishMarketReport1330Retry`
   - `autoPublishMarketReport1730Retry`
   - `autoPublishMarketReport2230Retry`
   - `autoPublishMarketReportsWatchdog`
6. 旧 `runMarketReportMaster...` と `MRWEB3...` の市場レポート発行ハンドラが残っていないことを確認する。
7. USD/JPYなど別用途のトリガーは、市場レポートの発行トリガーと混同しない。

### 5.1 現行の監視トリガー

現在の有効な市場レポートトリガーは、本発行4件、再試行4件、5分間隔のwatchdog 1件の合計9件である。Apps ScriptのshowMarketReportAutoPublishStatusで有効数と最終結果を確認する。ほかの用途のトリガーは削除しない。

## 6. GitHub変更の反映

1. 変更をブランチで検証する。
2. PythonテストとApps Scriptの構文確認を実行する。
3. 生成物4点の整合性、将来枠除外、訂正版、Driveレシートのブロッキングを確認する。
4. PRをレビューしてmainへマージする。
5. Apps Scriptへ同じ機能版を保存し、トリガーを再確認する。
6. 公開後にJSONと画面を照合し、反映記録へコミット・実行時刻・結果を書く。

変更前の正常コミットはロールバック用に保持する。公開中の本文やジョブ台帳を削除して復旧しない。

## 8. 禁止事項

- 本文未着を `ok:true` や成功として報告すること。
- 別時刻の本文を改名して欠落枠を埋めること。
- 同名・更新時刻だけでDriveの採用版を決めること。
- 本文の長さだけで新旧を判定すること。
- `latest-report.json` や `dashboard.json` を正本として本文を逆生成すること。
- 取得不能を0、古い値、推測値で補完すること。
- 保存レシートや実行結果を後付けで作ること。
- 公開JSONだけを見て画面確認済みと報告すること。

## 9. 連絡・エスカレーション

次のいずれかに該当したら、対象枠、`reportId`、状態、エラーコード、DriveファイルID、GitHubコミット、最後に成功した工程を添えて担当者へ引き継ぐ。

- `NEEDS_REVIEW` が自動再試行上限を超えた。
- 対象枠の採用候補が複数あり、本文比較でも決められない。
- Drive本文と公開本文のハッシュが一致しない。
- 公開先が前の版を返し続ける。
- 認証・権限エラーが解消しない。

## 11. TradingView MCPパイロット運用

### 11.1 試験中の扱い

TradingView MCPは、まず読み取り専用の補助入力として扱う。試験中にTradingViewの値だけで公開正本、`latest-report.json`、`dashboard.json`を置き換えない。本文には取得元と基準時刻を残す。

### 11.2 試験手順

1. CodexまたはChatGPTでTradingView MCPの認証状態を確認する。
2. `EXCHANGE:TICKER` を銘柄検索で解決する。
3. USD/JPYと金について、OHLCVとテクニカル値を読み取る。
4. 既存データ源の同じ基準日・時間足と比較する。
5. `source`、銘柄、時間足、バー時刻、取得時刻、取得結果、差異を記録する。
6. 取得失敗、再認証、レート制限、権限制限を原因コード付きで記録する。
7. 10稼働日分が揃うまで本番データ源を切り替えない。

### 11.3 本番昇格の条件

- 比較期間の差異と欠損が許容範囲内である。
- 対象日と時間足が既存データ源と一致する。
- 定時処理でOAuth認証を維持または再認証できる。
- 取得失敗時に既存データ源へ戻れる。
- 本文、Drive、正本、公開画面で取得元を追跡できる。

条件を満たさない場合は、TradingView MCPを補助表示または手動確認に限定する。

### 11.4 書き込みツールの扱い

Watchlistやアラートの作成・変更・削除などの書き込みツールは、マーケットレポート配信の初期パイロットでは使用しない。必要になった場合は、別の承認手順と監査記録を設ける。

改訂: v1.1 TradingView MCPを読み取り専用入力アダプターとして追加。本文・仕様・運用の本番切り替えゲートと10稼働日比較試験を追加。

## 12. 取得元の切替と復旧

通常運用は `sourceMode=legacy_only` とする。比較試験は `shadow` に変更し、本文と公開JSONは既存の検証済みデータ源で作成する。TradingViewへ昇格するときは、10稼働日の比較結果、OAuth、レート制限、取得元スナップショット、フォールバック試験がすべて確認できてから `tradingview_primary` に変更する。

次のエラーが1回でも発生した場合は、当該枠の公開を止め、設定を `legacy_only` に戻す。`AUTH_REQUIRED`、`RATE_LIMIT`、`TIMEOUT`、`SYMBOL_NOT_FOUND`、`DATA_MISMATCH`、`STALE_DATA`、`SCHEMA_INVALID`。復旧後は、対象枠、エラーコード、切替前後の設定、取得元、時刻、担当者を監査記録へ残し、Drive再読取と公開後照合を行う。

Apps Scriptでは `rollbackMarketReportDataSource('理由')` を実行すると、既存データ源へ戻り、変更履歴をScript Propertiesへ保存する。現在の既定値は既存データ源であり、TradingViewを有効化する変更は別途比較結果を確認してから行う。

## 13. 2026-09-25の反映漏れと標準復旧手順

### 13.1 確認された原因

08:00版は定時の事前検証時点で本文が不完全だった。12:00・16:00版はそれぞれの発行処理時点で対応するGoogle Docsが見つからなかった。本文が完全な状態でDriveへ保存された後も、Drive保存とポータル同期が別工程だったため自動で公開が再開しなかった。加えて21:00版は完全な本文と同時間帯の図解がDriveに保存された後、公開前検証で止まっていた。Apps Scriptの実行ログには「公開前検証に失敗しました。GitHubへの書き込みを中止します。」とあり、GitHubやdeployではなく本文解析段階の失敗だった。本文中の「メインシナリオは、」を見出し前方一致で空の節として扱い、小数値を番号付き見出しと誤認し、文章内に明示された市場価格を構造化値として読めず、本文の見出し別名も不足していた。いずれもUTC/JST変換ずれではない。

### 13.2 未反映を見つけた場合

1. 日付、対象時刻、reportId、Asia/Tokyoを確定し、起動時刻から対象枠を付け替えない。
2. Apps Scriptの実行履歴と最終結果を確認し、本文未検出、本文不完全、認証、GitHub更新、deploy、公開検証のどの工程で止まったか特定する。
   - `公開前検証に失敗しました。GitHubへの書き込みを中止します。` の場合はGitHubへ進む前に止まっている。本文の見出し判定、小数を含む行、市場別本文中の明示価格、必須セクション別名を確認し、原因を直した後に実レポート形式の回帰テストを実行する。
3. Driveで対象枠の正式なファイル名を探し、本文全体を再読取する。本文が完全でない場合は公開しない。
4. 本文と同一のYYYY-MM-DD_HH-MMを持つ既存図解があることを確認する。別時刻の図解を代用せず、存在しなければ対象枠を未発行として扱う。
5. Drive保存記録、正本JSON、reports.json、latest-report.json、dashboard.jsonを確認し、Build report indexとdeployのActions結果を追う。
6. 公開URLを開き、指定タイトル、本文、図解、日付・時刻選択を確認する。公開ページから取得できるまでVERIFIEDまたは公開済みと記録しない。
7. 全工程の対象枠、実行時刻、commit SHA、Actions、deploy、公開確認結果を記録する。

### 13.3 原本または画像がない場合

本文、仮の数値、別日・別時間帯の本文、図解を作成・流用しない。対象データなしとして記録し、未発行を利用者に示す。21:00枠は完全な本文と同時間帯の図解がそろう場合だけ公開する。
