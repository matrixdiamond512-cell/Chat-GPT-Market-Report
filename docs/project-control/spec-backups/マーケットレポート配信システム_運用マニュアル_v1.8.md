# マーケットレポート配信システム 運用マニュアル


文書版: v1.8\
改訂日: 2026-10-04


## 共通の確定契約


-   文書版: **v1.8**
-   タイムゾーン: `Asia/Tokyo`
-   新規レポート発行: **月〜金 08:00 / 12:00 / 16:00 / 21:00**
-   土曜・日曜: **レポート発行なし**
-   朝間市場データ更新: **06:30 JST**。これはレポート発行とは別工程。
-   対象識別子: `reportId=YYYY-MM-DD_HH-MM`
-   1営業日あたり: **本文4本 + 独立図解4枚**
-   08:00・12:00・16:00・21:00の全枠を図解対象とする。対象外扱いは禁止。
-   出力先: 指定済みChatGPT会話 **「Deliver weekday market reports」**
-   Codex作業チャット、別チャットへの代替出力を完了扱いにしない。


## 定期実行と責務分担


- レポートの唯一の定時実行元はChatGPTの定期タスクとする。現在の設定は月〜金の08:00、12:00、16:00、21:00 JSTである。
- 本文作成、指定ChatGPT会話への本文・図解表示、Google Drive保存と読戻し確認、GitHub登録、publication receipt、ポータル公開・再読込確認を、同じChatGPT実行が順に担当する。
- Apps Scriptの市場レポート用本発行・再試行・watchdogトリガーは無効にする。Apps Scriptの関数やソースが残っていることを、トリガー稼働中と解釈しない。レポート用トリガーのインストール関数を実行してはならない。
- 06:30の朝間市場データ更新はレポート発行とは別系統である。市場データ用トリガーをレポート用トリガーと混同したり、停止・削除したりしない。
- ChatGPT定期タスクの設定が有効でも、個別レポートの実行・保存・公開成功を意味しない。各対象枠の工程結果を別々に確認する。


## 正式トランザクション順序


1. 対象枠と `reportId` を固定し、市場データ・ニュース・イベントを取得して検証する。
2. 指定ChatGPT会話「Deliver weekday market reports」に、対象時刻・タイトルと本文全文を表示する。
3. 直後に同じ本文だけを根拠にした独立図解を1枚表示する。図解用に本文外の値を取得・追加しない。
4. チャットに表示した本文の完全な原文を保持し、同一の全文を月別のGoogle Drive本文フォルダー（`マーケットレポートYYYY年MM月`）へ保存する。既存の対象Docを優先し、空の重複Docを作らない。
5. 保存直後に同じGoogle Docsファイルを再読取する。タイトル、全セクション、全数値、末尾の確認結果まで原文全文と一致することを確かめる。文字数、先頭一致、ハッシュだけで代替しない。
6. 対応する図解をPNGとして月別のGoogle Drive図解フォルダー（`マーケットレポート図解YYYY年MM月`）へ保存する。名前は `マーケットレポート_YYYY-MM-DD_HH-00.png` とし、ファイルの存在と対象枠を確認する。
7. 本文の全文一致と対応PNGの保存確認が両方成功した場合だけ、同一本文と図解をGitHubへ登録する。
8. Google Docs保存・図解保存の検証後にpublication receiptを含む公開バンドルを生成し、GitHub登録成功後にreceiptの公開反映を確認する。
9. publication receiptを含む公開バンドルのGitHub登録と検証成功後だけGitHub Pages／ポータルへ公開する。
10. 公開後にページを再読込し、対象日時、タイトル、本文、図解対応を確認する。


本文・図解の表示、Drive本文検証、Drive図解確認、GitHub、receipt、ポータルのどこかで失敗した場合は、その工程で停止する。後続を成功扱いにせず、停止工程と理由を記録する。


## 原本保全・復元禁止


-   原本が不在、空、読取不能、欠落、切断、検証不一致の場合、本文または図解を推測・再構成・補完・捏造しない。
-   別日・別時刻・後から取得した値を原本の代用にしない。
-   後日作成した復旧版を「当時の原本」と表示しない。
-   原本がない枠は未発行／待機として扱い、停止工程と理由を記録する。


## 図解契約


-   08:00・12:00・16:00・21:00すべてで1レポートにつき独立画像1枚。
-   図解は同一枠の本文に明記された事実・数値・分析・因果関係だけを使用する。
-   本文にない情報を検索・補足して図解へ追加しない。
-   時刻をまたいで複数レポートを1枚に結合しない。
-   Mermaidは補助表現として利用可能だが、**Mermaid限定ではない**。標準成果物は可読性の高い独立図解画像1枚。
-   装飾的なチャートを優先せず、表、短評、矢印、アイコン、色分けパネルで因果関係と監視点を示す。


## 最終ステータス


各対象枠の最後に、以下を別々に判定する。


- `チャット本文：出力済み／未出力`
- `図解：表示済み／未表示`
- `Google Docs：保存済み／未保存／検証失敗`
- `図解Drive：保存済み／未保存／検証失敗`
- `GitHub：登録済み／未登録`
- `publication receipt：作成済み／未作成`
- `ポータル：反映済み／未反映／確認失敗`


部分成功を全体成功として報告しない。


## 定時運用


### 現行設定


- ChatGPT定期タスク「平日マーケットレポートと図解をChatGPTのレポートチャットに表示」が唯一のレポート用スケジュールである。
- 2026-10-03に確認した設定は `ACTIVE`、月〜金の08:00・12:00・16:00・21:00 JST、出力先は指定会話「Deliver weekday market reports」。
- Apps Scriptの市場レポート用本発行4件・再試行4件・5分watchdogは停止済み。レポート用トリガーを再インストールしない。市場データ更新など他用途のトリガーは残す。
- 06:30の朝間市場データ更新は別工程。仕様上の予定時刻だけで、当日の実行成功を判断しない。
- 定期タスクが `ACTIVE` であることは設定の確認であり、本文・図解・保存・公開の成功を証明しない。2026-10-03時点では、一本化後の全工程を通した実行は未確認。次の予定実行後に対象枠ごとに確認する。


### 設定確認手順


1. ChatGPTの定期タスク一覧で、上記タスクが1件だけ `ACTIVE` であること、平日4時刻、指定会話を確認する。
2. Apps Scriptのトリガー一覧で、レポート本発行・再試行・watchdogが0件であることを確認する。
3. 市場データ更新など別用途のトリガーは残っていることを確認し、レポート用トリガーと混同しない。
4. ChatGPT側とApps Script側に同じレポート枠の定期発行が重複していないことを確認する。


## SOP


対象枠固定 → 情報取得 → クロスチェック → ChatGPT会話へ本文全文と図解を表示 → Google Docs保存・同一Doc再読取で全文一致 → 対応PNGをDrive保存・存在確認 → GitHub登録 → receipt作成 → portal公開 → 公開ページ再読取 → 個別ステータス報告。Apps Scriptのレポート用トリガーは起動しない。


## 障害時


Doc不在・空・本文不一致・読取失敗では停止し、別Docを乱造しない。原本不在時は復元しない。GitHub失敗時はreceiptを作らない。receipt失敗時はportal完了扱いにしない。公開ページが旧版ならVERIFIEDにしない。


## 完了報告


「完了」は全ゲートを通過した場合のみ使用する。部分成功では各工程を個別表示する。チャット本文が実際に表示されていない場合は必ず
`チャット本文：未出力` とする。

## v1.8 2026-10-04 統合追補：公開障害・表示QA・市場表QA


### 公開完了の判定


Google Docs保存、GitHubコミット、GitHub Pagesビルドの単独成功を公開完了としない。以下をすべて別工程として確認する。


1. Google Docs実体と本文全文
2. Drive保存証跡
3. canonical report
4. reports.json
5. latest-report
6. dashboard currentReportKey
7. GitHub Actions
8. GitHub Pages
9. 公開DOM
10. 主要市場データ表・見出し・時間帯別レイアウト


部分成功は部分成功として報告する。


### 公開障害の切り分け


画面が「本文データを読み込んでいます。」のまま10秒以上停止、日付が空、時間帯タブが出ない、reports.json取得済みなのに本文DOMがない場合は、レポート本文を再生成する前に以下の順で確認する。


reports.json HTTP取得 → 対象reportId存在 → 表示JavaScript取得 → 構文エラー → init → reports配列 → selectedReport → render処理 → DOM → キャッシュ。


データが正常で表示だけ停止している場合は「公開障害」とし、「レポート欠落」と誤判定しない。


### JavaScript変更時


`node --check` 等の構文確認、致命的Consoleエラーなし、version query更新、通常URLでの再読込確認を必須とする。JavaScript本体だけ変更してキャッシュversionを据え置かない。


### 主要市場表QA


公開前に以下を確認する。


- 主要市場データ見出しが独立セクションである。
- 直下がmarket-table相当であり通常段落の羅列ではない。
- 市場名、値、前日比、騰落率、方向列が表示される。
- 取得不能値は理由付き。
- 08:00は前営業日終値表。
- 12:00・16:00・21:00は現在値・確認値表。
- モバイル幅で列崩れ・文字切れがない。


### 公開成功の追加条件


主要Actions、Pages、実ブラウザー、日時切替、前日・翌日、通常URL再読込、主要市場表、主要SOP見出しのセクション化まで確認して初めて「公開完了」「直った」と報告する。


### 2026-10-04障害記録


表示停止ではJavaScriptソースへの不正なリテラル `\n` 混入が確認された。また公開パイプラインではreports.json形式、canonical/index、latest、dashboard、Drive保存証跡、SOP必須見出し、revision/updatedAtの不整合が複合していた。主要市場データが通常段落になる障害では、Google Docs由来のプレーン見出しをレンダラーが認識できないことが原因だった。これらを今後の標準切り分け・回帰テスト対象とする。
