## ステージ別の実装指示
### P0（外部依存なしで先行実装してよい候補）
1. `scripts/resolve_market_report_slot.py` の現行契約を調査し、`scheduleTimeUTC`（予定時刻）又は明示的な `reportDate+reportSlot` から`reportId`を一度だけ決める純粋関数を提案／追加。JSTの日付繰越を厳密に扱い、無効・未来・過去不適格なスロットを区別して拒否。
2. `scripts/run_market_data_window.py` の `now_jst().date()` 再決定依存を、引数（`--report-date`）で固定できるよう設計。引数省略のlegacy挙動と誤混用をテストし、既存本番workflowはこの段階で変更しない。
3. 変更対象以外のファイルに触れず、`tests/test_market_data_window_evidence.py`、`tests/test_report_slot_evidence.py`等に日付跨ぎ・遅延・重複・T跨ぎ・再実行の回帰を追加。旧テストを維持。
4. 発行準備判定を`acquisitionReady`、`evidenceReady`、`draftAllowed`、`publicationEligible`の独立した純粋な判定に分ける候補を設計。証拠不足で`draftAllowed`を一律falseにしないが、`publicationEligible`は常にfalseを維持。

### P1（独立証拠経路のshadow実装）
1. Cloud Scheduler予定時刻（`X-CloudScheduler-ScheduleTime`等）に対応するオリジナルslotを、設定された`T-13/T-7/T-3`試行から一意に導出。壁時計`now`から元スロットを再計算しない。署名認証・OIDC検証方式を設計。
2. Cloud Runジョブ側の`JobCoordinator`・`EvidenceWriter`インターフェースを作成。Cloud Storageにcreate-only（ifGenerationMatch=0）で書き込み、generation+SHA256+サーバ確定時刻で読戻す。書込みの前後でT超過判定し、Tを超えて確定した証拠は公式に採用しない。
3. 同一reportId/同一bytesのNO_OPと異なるbytesのCONFLICTを区別。段階ごとの永続状態、リトライと排他制御の契約テストを作る。実クラウド権限なしでもFakeストレージで再現する。
4. shadowモードでは公式`data/report-evidence`、Docs、reports.json、receipt、Pagesに一切書き込まない。コスト見積もり、実行ロール/Secret計画と切替前に必要な入力を出す。
5. 本番用のCloud Scheduler/Cloud Run/Storage資源は作成しない。設定方法・IAM最小権限・実行時間制約だけを説明文書にする。
