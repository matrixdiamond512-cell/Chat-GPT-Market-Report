# マーケットレポート配信システム 仕様書


文書版: v1.8\
改訂日: 2026-10-04


## 共通の確定契約


-   文書版: **v1.8**
-   タイムゾーン: `Asia/Tokyo`
-   新規レポート発行: **月〜金 08:00 / 12:00 / 16:00 / 21:00**
-   土曜・日曜: **レポート発行なし**
-   朝間市場データ更新: **06:30 JST**。これはレポート発行とは別工程。
-   対象識別子: `reportId=YYYY-MM-DD_HH-MM`
-   1営業日あたり: **本文4本 + 独立図解4枚**
-   08:00・12:00・16:00・21:00の全枠を図解対象とする。対象外扱いは禁止。
-   出力先: 指定済みChatGPT会話 **「Deliver weekday market reports」**
-   Codex作業チャット、別チャットへの代替出力を完了扱いにしない。


## 定期実行と責務分担


- レポートの唯一の定時実行元はChatGPTの定期タスクとする。現在の設定は月〜金の08:00、12:00、16:00、21:00 JSTである。
- 本文作成、指定ChatGPT会話への本文・図解表示、Google Drive保存と読戻し確認、Publication Manifest、GitHub登録、Actions、ポータル公開・再読込確認、Publication Receiptを、同じChatGPT実行が順に担当する。
- Apps Scriptの市場レポート用本発行・再試行・watchdogトリガーは無効にする。Apps Scriptの関数やソースが残っていることを、トリガー稼働中と解釈しない。レポート用トリガーのインストール関数を実行してはならない。
- 06:30の朝間市場データ更新はレポート発行とは別系統である。市場データ用トリガーをレポート用トリガーと混同したり、停止・削除したりしない。
- ChatGPT定期タスクの設定が有効でも、個別レポートの実行・保存・公開成功を意味しない。各対象枠の工程結果を別々に確認する。


## 正式トランザクション順序

1. 明示されたReportContext（対象日・時刻・report_id・revision）とimmutable MarketDataSnapshotを固定する。
2. 指定ChatGPT会話へ本文原文全文を表示し、原文を保持する。
3. 同じ本文・snapshot・report_id・revisionの図解を表示する。
4. 同一Google Docs fileIdへ本文を保存する。
5. 保存先と同じfileIdを再読取し、限定normalizationと前後diffで全文一致を検証する。
6. 対応PNGのDrive実在、filename、bytes、本文・snapshot・版の一致を検証する。
7. Publication Manifestを生成する（READY_FOR_PUBLICATION）。receiptは公開前bundleに含めない。
8. 同じManifestのcanonical / reports.json / latest / dashboardの整合とrevision後退防止を検証し、GitHubへ登録する。
9. 同一commit SHAのGitHub Actions成功とGitHub Pages deploymentを確認する。
10. 公開DOMの本文・市場表・PNG・操作・timeout・mobile・consoleを検証する。
11. 公開検証後だけPublication Receiptを生成し、Manifest・Git SHA・Pages・DOM証拠へ結び付ける。
12. 全証拠が揃った場合だけVERIFIEDとする。失敗は停止し、外部効果不明はUNKNOWNのまま再試行前に照合する。

本文・図解の表示、Drive本文検証、Drive図解確認、Manifest、GitHub、Actions、ポータル検証、Receiptのどこかで失敗した場合は、その工程で停止する。後続を成功扱いにせず、停止工程と理由を記録する。


## 原本保全・復元禁止


-   原本が不在、空、読取不能、欠落、切断、検証不一致の場合、本文または図解を推測・再構成・補完・捏造しない。
-   別日・別時刻・後から取得した値を原本の代用にしない。
-   後日作成した復旧版を「当時の原本」と表示しない。
-   原本がない枠は未発行／待機として扱い、停止工程と理由を記録する。


## 図解契約


-   08:00・12:00・16:00・21:00すべてで1レポートにつき独立画像1枚。
-   図解は同一枠の本文に明記された事実・数値・分析・因果関係だけを使用する。
-   本文にない情報を検索・補足して図解へ追加しない。
-   時刻をまたいで複数レポートを1枚に結合しない。
-   Mermaidは補助表現として利用可能だが、**Mermaid限定ではない**。標準成果物は可読性の高い独立図解画像1枚。
-   装飾的なチャートを優先せず、表、短評、矢印、アイコン、色分けパネルで因果関係と監視点を示す。


## 最終ステータス


各対象枠の最後に、以下を別々に判定する。


- `チャット本文：出力済み／未出力`
- `図解：表示済み／未表示`
- `Google Docs：保存済み／未保存／検証失敗`
- `図解Drive：保存済み／未保存／検証失敗`
- `GitHub：登録済み／未登録`
- `publication receipt：作成済み／未作成`
- `ポータル：反映済み／未反映／確認失敗`


部分成功を全体成功として報告しない。


## 定期実行の実装契約


ChatGPTの有効な定期タスク1件を唯一のレポート用スケジュールとし、月〜金の08:00・12:00・16:00・21:00 JSTに同一の全工程を実行する。Apps Scriptの4件の本発行、4件の再試行、5分watchdogは停止し、重複実行元として再インストールしない。Apps Script内に関数が残っていても、トリガー一覧に登録されていなければ定時実行されない。市場データ更新など別用途のトリガーはこの停止対象に含めない。


ChatGPT定期タスクの設定確認は設定レベルの証拠である。レポート本文、図解、Drive、Manifest、GitHub、Actions、ポータル検証、Receiptの各実行結果を確認するまで、動作成功とは判定しない。


## 状態遷移


`WAITING_INPUT → CHAT_BODY_OUTPUT → INFOGRAPHIC_OUTPUT → DRIVE_WRITTEN → DRIVE_VERIFIED → PNG_VERIFIED → MANIFEST_READY → GITHUB_REGISTERED → ACTIONS_PASSED → PORTAL_PUBLISHED → DOM_VERIFIED → RECEIPT_CREATED → VERIFIED`


失敗状態は `RETRYABLE_FAILED` と `NEEDS_REVIEW`
を用いる。Drive全文一致前に `GITHUB_REGISTERED` へ遷移してはならない。


## Drive全文一致仕様


比較対象はチャットへ表示した原文全文と、保存直後に同一fileIdから読み戻した本文全文。改行コード等の保存系が不可避に正規化する場合は、意味を変えない事前定義済みの正規化だけを両側へ同一適用し、差分ログを残す。要約比較、文字数比較、先頭比較だけで合格にしない。


## 図解PNGのDrive保存


本文と同じ `reportId` の独立画像をPNGで保存する。対象フォルダーは `マーケットレポート図解YYYY年MM月`、ファイル名は `マーケットレポート_YYYY-MM-DD_HH-00.png` とする。保存後にDriveから同じファイルを確認し、ファイル名とreportIdが一致するまでGitHubへ進まない。別枠画像の代用は禁止する。


## GitHub / receipt / portal


`reports/<reportId>.json`
に検証済み本文全文を保持する。プレースホルダー、空文字、要約で
`fullText`
を代用しない。公開DOM検証前にReceiptを作らない。公開後は公開URLから対象reportId、タイトル、本文、図解対応を確認する。


## 図解


画像キーは本文と同じ
`YYYY-MM-DD_HH-MM`。4枠すべて必須。本文外情報の追加は禁止。生成失敗は
`図解：未表示` とし、成功扱いにしない。


## 冪等性


同じreportId・revision・本文に対する再試行では既存成果物を確認し、空Docや重複Docを作らない。保存応答が不明な場合も既存fileIdと内容を照合してから再送する。

## v1.8 2026-10-04 統合追補：公開パイプライン・レンダラー契約


### 1. 公開データ契約


- `reports.json` のルートは必ずJSON配列とする。ラッパーオブジェクト、latestReport単体、同一date/time重複は禁止。
- `reports/<reportId>.json` をcanonical reportとする。
- `reports.json` の同一スロット内容はcanonical reportと一致させる。
- `data/latest-report.json` は公開対象の最新canonical reportと一致させる。
- `data/dashboard.json.currentReportKey` はlatest-reportのdate/timeと一致させる。
- 同一date/timeの訂正には `revision` または `updatedAt` を必須とし、旧版の逆上書きを拒否する。


### 2. Google Drive保存証跡


Drive保存証拠はPublication Manifestのdrive_file_id/drive_url/body_hashへ保持する。本文原文と同一fileIdからの全文読戻し、文書タイトル、report_idを検証する。Receiptは公開結果を記録し、本文保存証拠だけでVERIFIEDにしない。


### 3. 公開処理の正規順序


対象枠固定 → データ取得・検証 → Chat本文 → 図解 → Google Docs保存・全文再読取 → PNG保存確認 → Publication Manifestを含む公開バンドル生成（Receiptを含めない） → canonical / latest / reports.json / dashboard同期 → GitHub登録 → Actions検証 → Pagesデプロイ → 公開DOM再読込確認 → Publication Receipt生成 → VERIFIED。


公開前はManifestだけを生成する。Receiptは同じGit SHAの公開DOM検証後に生成する。どの段階でも不整合があれば停止する。


### 4. JavaScript / DOM契約


report.htmlまたは表示用JavaScriptを変更した場合は、少なくとも以下を必須とする。


- JavaScript構文チェック。SyntaxError / ReferenceErrorを残さない。
- コード境界へ意図しないリテラル `\n` / `\r` 等を混入させない。
- 主要レンダラーが最後まで読み込まれ、init・選択・render処理が完走すること。
- script srcのversion queryを更新し、通常URLでも新コードが読み込まれること。
- 日付、時間帯タブ、reportStatus、本文、前日・翌日、日時切替を実DOMで確認する。
- 「本文データを読み込んでいます。」が10秒以上残る場合は表示障害とする。


### 5. 見出し認識契約


次の3系統を正式サポートする。


1. Markdown / 番号 / 【】付きの構造化見出し。
2. Google Docs由来のプレーンテキスト見出し。
3. 今後追加するSOP見出し。


プレーン見出しには、今日の相場テーマ、前回からの変化、主要市場データ、材料と値動きの整合性、今日の主導市場、重要ニュース、金利、クロスアセット資金フロー、需給・ポジション、重要イベント、個別市場見通し、シナリオ、シナリオが崩れる条件、各時間帯への引き継ぎ、リスク管理、結論、クロスチェック結果等を含める。


本文側に新しい見出しを追加した場合は、表示側の `plainHeadings` 相当ルールとQAも同時に更新する。


### 6. 主要市場データ表契約


「主要市場データ」「主要市場まとめ」「市場データ」「前営業日終値」「終値一覧」「主要価格」は通常段落ではなく表としてレンダリングする。


通常時間帯の基本列：
市場・指標 / 現在値・確認値 / 前日比 / 騰落率 / 方向・状態


08:00前営業日終値表の基本列：
項目 / 終値・値 / 前日比 / 騰落率 / 方向感


表データ優先順位：
1. `report.marketDataTable.rows`
2. `report.markets`
3. `fullText` からのlegacy抽出


08:00版で `marketDataTable.rows` が存在する場合は本文推測による行追加を行わない。取得不能値は理由付き文字列として保持する。


### 7. レンダラー変更時の回帰テスト


構文チェックだけでは完了としない。08:00 / 12:00 / 16:00 / 21:00について、主要市場表、見出し階層、時間帯切替、モバイル表示、実公開ページが同一コードで正常であることを確認する。

## 2026-10-04 Manifest / Receipt契約確定（SC-01〜03解消）

Publication Manifestは公開前の固定契約。必須fieldは `manifest_id`, `report_id`, `report_date`, `report_time`, `revision`, `body_hash`, `snapshot_id`, `drive_file_id`, `drive_url`, `png_file_id`, `png_filename`, `created_at`。状態はREADY_FOR_PUBLICATION。PNG欠落・不一致ではManifest FAILとし、新規GitHub登録／Pages公開の許可を発行しない。

Publication Receiptは公開後の結果証拠。必須fieldは `report_id`, `revision`, `manifest_id`, `manifest_hash`, `git_commit_sha`, `pages_deployment_id`, `published_at`, `verified_at`, `portal_url`, `dom_validation_status`, `final_status`。PUBLISHED / VERIFIED / FAILED / UNKNOWNを区別する。公開前bundleには含めず、全公開検証後に生成する。既存過去receiptは読取互換として保持し、一括変換・削除しない。

ReportContextは入口で一度生成してreadonly、retryでも同一値を再使用する。report_date/report_timeは明示入力。unknown cronはfail closed。土日は新規発行なし。historical/recoveryは明示modeと対象日時で別扱い。attempt_id/execution_started_at/saved_at/published_at/verified_atはExecutionContextへ分離する。市場取得（月〜土06:30等）は発行とは独立する。

Snapshotは同一report_id・revision・data_cutoffに固定する。本文生成後のlatest混入・Docs/PNG/JSON/portalでの再取得は禁止。新価格は新revision。ReportObjectはreport_id/report_date/report_time/revision/snapshot_id/title/full_text/sections/market_data_table/markets/previous_report_id/statusを持つ。数値とdisplayText、観測directionとoutlook、0/null/UNAVAILABLE/STALE/N/Aを区別する。

全文照合で許すnormalizationはCRLF/LFと末尾単一改行のみを初期実装とする。Drive由来空行は別途根拠と限定ruleが承認されるまで自動吸収しない。句点・文章・表現・数値変更は不一致。normalize前後diffを保持する。

2026-10-02_21-00はcanonicalIdentity=UNRESOLVED、publicationStatus=UNVERIFIED、reviewStatus=NEEDS_REVIEWとして保全する。OLD削除、NEW自動統一、canonical/receipt書換え、PNG再生成は禁止。

今回の実装はA→B→D→Cと回帰確認まで。E〜HのPublisher / Projection / Portal / Scheduler再編・本番データ変更・push/deployは実施しない。過去v1.7等の順序記述は履歴であり、本節の現行契約を優先する。
