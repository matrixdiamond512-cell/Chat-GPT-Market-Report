## 2. 実装前の最優先ゲート：生成元から原文証拠を取得できるか
GATE-F0として、実際のChatGPT定期タスク08:00・12:00・16:00・21:00の実行ごとに、機械的に検証可能な実行識別子、原文全文、生成日時、生成完了状態を、権限を持つ正式な連携から取得できるか実証する。
サンプルのコピー／手入力／Google Docsから逆算した本文／チャットの自己申告のみではPASSにしない。取得した原文のハッシュが、ChatGPT上に実際に表示された原文と一致することを、取得元・取得時刻・原文版を伴う証跡で説明する。
GATE-F0判定は PASS / BLOCKED_UNAVAILABLE / BLOCKED_UNVERIFIED とし、証拠としてAPI/コネクタ仕様、権限、実行ログ、原文ハッシュ、保存先を残す。取得経路未確立なら後続の本番デプロイ・公開は行わない。
ChatGPTタスクから取得できない場合は、A：正式な出力連携の調査継続、B：OpenAI APIを利用する専用生成ワーカーへの移行案（追加費用・権限・定時運用・再現性・保存先を提示）の2案を比較して承認待ちとする。移行は自動決定・無断実装しない。

## 3. システム責務と信頼境界
生成元（producer）は、時刻確定、ReportContextの作成、所定の市場データ取得・検証、MarketDataSnapshot凍結、AI本文生成、原文の版固定、原文ハッシュ計算、ChatGPT出力との照合、発行証拠の記録を担当する。
保存担当は、生成元の同一原文をGoogle Docsへ保存し、ファイルID、Docs revision、読み戻し本文全文、保存時刻、読み戻しハッシュを返す。Google Docsの更新時刻からReportContext.revisionを推測してはならない。
署名担当は、producerが確定した証拠のみを認証し、公開者がその証拠を自己生成できない責任分離を備える。署名権限と公開権限の分離・認証鍵の管理方式を実証する。
Apps Script公開担当（publisher）は、保存済みDocsと独立の署名付きproducer証拠を照合し、全条件PASSでのみGitHub正本・reports.json・latest/dashboard・receipt公開へ進む。証拠そのものをDocsやdata/latestから捏造しない。
図解（PNG）の品質管理は本文公開の独立レーンのままとする。ただし図解のreport/revision/snapshot/bodyHash紐付けは検証する。

## 4. 生成・保存・公開のデータ契約
識別子は「YYYY-MM-DD_HH-MM」を唯一の内部report_idとする。可視タイトルは「マーケットレポート｜YYYY/MM/DD（曜）HH:MM」。内部revisionはproducerの正整数であり、Drive mtimeは使わない。
ReportContextは既存 scripts/reporting/context.py のフィールド・検証を基準とする。必須：report_date, report_time, report_id, data_cutoff（TZ付き）, previous_report_id（該当時）, previous_business_day, revision, mode。
Snapshotは既存 scripts/reporting/snapshot.py の内容・source/status/asOfと凍結時刻を基準とし、snapshot_id, report_id, revision, schema_version, captured_at, data_cutoff, marketsを保持する。保存後に値を上書き・再取得しない。各asOfはdata_cutoffを超えてはならず、過去枠へ事後取得したデータを付け直してはならない。
原文証拠には producer_run_id、生成時刻、生成完了状態、実際の原文の独立参照（取得可能な正式なmessage/execution ID等）、producer_body_sha256、原文の取得方法、取得元の証跡を保持する。chat_evidence_idを文字列として埋めるだけでは受入不可。
Docs保存証拠には source_document_id、保存時刻、readback時刻、Google Docs revision、Docs本文SHA-256、上流producer_run_idを保持する。
公開用の署名済みエンベロープは、report_id/revision、context、context digest、snapshot、snapshot_id、producer原文ハッシュ、信頼できる原文参照、Docs ID、issuer識別子、署名対象と署名方式・版、署名値、証拠保管先の不変参照を含む。PR #130の producer-proof/YYYY-MM-DD_HH-MM.json は暫定検証側のパスであり、真正なissuer発行方法とschema凍結前は本番証拠と認定しない。
同一report_idの再発行はrevision単調増加と元レポートの不変履歴を条件とする。内容相違がある同revisionは拒否。重複Docsがあっても自動的に片方を正本として選ばない。

## 5. ハッシュ・署名・改ざん検証
原文ハッシュはproducer側で確定した全文のUTF-8 SHA-256を真値とする。Docsから読み出してpublisherが新しく作った値を「期待値」として採用してはならない。
改行のCRLF/LF、文末改行、Unicode、空白、Google Docs構造上の差について、producerの原文とDocs readbackの明示的な正規化契約を一つだけ定義する。数字・句読点・市場データ・見出しを修正／削除する正規化は禁止。raw hashとcanonical hashを別々に残し、差分を保存する。
既存Pythonの snapshot.digest（json.dumps sort_keys / ensure_ascii=False / separators）とApps Scriptの marketReportProofCanonical_（JSON.stringify相当）には数値などのシリアライズ差があり得る。Pythonで生成した日本語・小数・100.0・null・負数・日時・市場配列のgolden fixturesをGASで照合し、同じバイト列・snapshot_id・context digest・署名結果になるまで本番化しない。
整合しない場合は勝手に過去snapshot_idを再計算しない。canonicalizationの規格・フィールド型・小数表現・schemaVersionの移行計画を先に定める。
PR #130のHMAC方式は共有秘密で検証者も署名を作れるため、独立したproducer署名の完全な権限分離を示すものではない。実運用では、producer専用署名鍵＋publisherに検証専用権限を与える方式（非対称署名、または独立認証サービス）を比較実証する。鍵はGitHub公開リポジトリ、Google Docs、ログに載せない。署名の正しさと「実ChatGPTがその本文を生成した証拠」は別々に確認する。

## 6. 実際の公開処理での必須チェック
順序は①正規report_id/対象枠、②署名付きproofの存在と信頼できる発行元、③context・snapshot・cutoff・市場元データの整合、④ChatGPT原文独立照合、⑤Docs保存ID/revision/readback/原文ハッシュ照合、⑥公開本文構造・見出し・市場データSOP、⑦競合revision/二重登録防止、⑧GitHub書込である。
最初のGitHub書込前に全てPASSとする。失敗時は BLOCKED とし、原因コード、report_id、slot、producer_run_id、取得証拠参照、チェック時刻を記録する。例外本文とstackを秘匿情報なしで残す。
対象経路：publishWebReportObject_（手動/共通）、publishMarketReportSlot_（定時・retry・watchdog）、archiveMarketReportFromDriveWithoutLatestRollback_（アーカイブ）、MarketReportStructuredImport.gs、MarketReportHistoricalImport.gs、reports.jsonを独立更新する他のwriter。GitHub APIへ直接書く新経路があれば同じゲートを追加する。
旧いレポートでproofが見つからない場合、見出しが正しくても公開を禁止する。復旧処理をバイパスや「後付けのsnapshot」で代用しない。既公開レポートの安易な一括削除・置換もしない。
公開成功はGitHub commitだけでなく、正本、reports.json、latest-report.json、dashboard.json、公開receipt、Pages上のレポート本文readbackを同一report_id/revision/bodyHashで照合して判定する。
